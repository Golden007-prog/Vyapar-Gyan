# Requirements Document

## Introduction

The WhatsApp Voice Pipeline adds end-to-end voice message support to VyaparGyan's existing WhatsApp commerce channel. When a seller or customer sends a voice note on WhatsApp, the system downloads the audio from Twilio, transcribes it via Gemini, feeds the transcript into the existing agent/copilot pipeline, generates a spoken reply via Gemini TTS, and sends the voice reply back through Twilio as a WhatsApp audio message. All existing text-message behavior remains unchanged. The feature reuses the current Twilio webhook → Lambda → EventBridge/SQS → worker architecture and preserves demo identities and store routing.

## Glossary

- **Voice_Pipeline**: The end-to-end flow from inbound WhatsApp voice note reception through transcription, agent processing, TTS generation, and outbound voice reply delivery
- **Webhook_Handler**: The existing Lambda function (`webhook.ts`) that receives inbound Twilio WhatsApp webhooks, validates signatures, and publishes events to EventBridge
- **WhatsApp_Worker**: The existing SQS-triggered Lambda function (`worker.ts`) that processes inbound WhatsApp messages by role (seller/customer) and media type (text/audio/image)
- **Gemini_Adapter**: The existing adapter (`gemini-adapter.ts`) that interfaces with Google Gemini for transcription, OCR, and image analysis
- **Twilio_Adapter**: The existing adapter (`twilio-adapter.ts`) that sends outbound WhatsApp messages via Twilio's API, supporting text and media
- **WhatsApp_Sender**: The existing service (`whatsapp-sender.ts`) that formats, sanitizes, persists, and sends outbound WhatsApp messages
- **Seller_Copilot**: The existing agent service (`seller-copilot.ts`) that processes seller WhatsApp commands (stock checks, price updates, order views, approvals)
- **State_Router**: The existing message router (`router.ts`) that directs customer messages to greeting, browsing, or checkout handlers based on session state
- **Sanitizer**: The existing module (`whatsapp-sanitizer.ts`) that strips JSON, XML, debug strings, and internal errors from outbound messages
- **Media_Processing_Worker**: The existing SQS-triggered Lambda (`media-processing-worker.ts`) that handles voice note transcription and image search for customers
- **Session_Service**: The existing service (`session-service.ts`) that resolves or creates unified sessions spanning WhatsApp and web channels
- **TTS_Audio**: Audio content generated by Gemini Text-to-Speech, formatted as OGG/Opus for WhatsApp voice note delivery
- **Voice_Media_Bucket**: The S3 storage location (existing media bucket) used for temporary inbound and outbound voice audio files
- **Transcript**: The text output produced by Gemini from an inbound voice note, including detected language and confidence signals
- **Audio_Validation**: The process of checking inbound audio for supported MIME type, file size limits, and format compatibility before processing

## Requirements

### Requirement 1: Inbound Voice Note Detection and Download

**User Story:** As a WhatsApp user (seller or customer), I want to send a voice note so that the system understands my spoken request without requiring me to type.

#### Acceptance Criteria

1. WHEN the Webhook_Handler receives a Twilio webhook where `MediaContentType0` starts with `audio/`, THE Webhook_Handler SHALL set the message type to `audio` and include the media URL in the transformed payload
2. WHEN the WhatsApp_Worker receives a message with type `audio`, THE WhatsApp_Worker SHALL download the audio binary from the Twilio media URL using authenticated HTTP requests with Twilio credentials
3. WHEN the WhatsApp_Worker downloads inbound audio, THE WhatsApp_Worker SHALL store the audio in the Voice_Media_Bucket under the key pattern `voice/inbound/{userId}/{timestamp}.ogg`
4. IF the Twilio media URL is unreachable or returns a non-200 status, THEN THE WhatsApp_Worker SHALL send a text fallback asking the user to resend or type their request
5. THE WhatsApp_Worker SHALL log the audio receipt event with userId, message ID, MIME type, and file size in bytes

### Requirement 2: Inbound Audio Validation

**User Story:** As a platform operator, I want inbound voice notes validated before processing so that the system rejects unsupported or oversized audio files gracefully.

#### Acceptance Criteria

1. WHEN the WhatsApp_Worker receives an audio message, THE WhatsApp_Worker SHALL validate that the MIME type is one of `audio/ogg`, `audio/opus`, `audio/mpeg`, or `audio/mp4`
2. WHEN the WhatsApp_Worker receives an audio message, THE WhatsApp_Worker SHALL validate that the audio file size does not exceed 16 MB
3. IF the audio MIME type is not in the supported list, THEN THE WhatsApp_Worker SHALL send a text message to the user stating that the audio format is not supported and asking the user to send an OGG voice note or type the request
4. IF the audio file size exceeds 16 MB, THEN THE WhatsApp_Worker SHALL send a text message to the user stating that the voice note is too long and asking the user to send a shorter message
5. THE WhatsApp_Worker SHALL log validation failures with userId, MIME type, file size, and rejection reason

### Requirement 3: Voice Transcription via Gemini

**User Story:** As a WhatsApp user, I want my voice note transcribed accurately in my spoken language so that the system understands what I said.

#### Acceptance Criteria

1. WHEN the Voice_Pipeline receives validated audio, THE Gemini_Adapter SHALL send the audio to Gemini for transcription with a multilingual prompt supporting English, Hindi, and other Gemini-supported spoken languages
2. WHEN the Gemini_Adapter completes transcription, THE Gemini_Adapter SHALL return a Transcript containing the full transcription text, the detected spoken language, and a confidence score between 0 and 100
3. IF the Gemini transcription returns an empty transcript or a confidence score below 30, THEN THE Voice_Pipeline SHALL send a text clarification message to the user asking them to repeat or rephrase, without hallucinating intent
4. THE Gemini_Adapter SHALL accept audio in OGG, Opus, MPEG, and MP4 formats for transcription
5. THE Voice_Pipeline SHALL log the transcription result with userId, detected language, confidence score, and transcript length

### Requirement 4: Transcript Routing to Agent Pipeline

**User Story:** As a seller, I want my spoken commands (stock checks, price updates) processed the same way as typed commands so that voice input works seamlessly with the existing copilot.

#### Acceptance Criteria

1. WHEN the Voice_Pipeline produces a valid Transcript for a seller user, THE WhatsApp_Worker SHALL pass the transcript text to the Seller_Copilot as the message input, preserving the same user context, phone number, and request ID used for text messages
2. WHEN the Voice_Pipeline produces a valid Transcript for a customer user, THE WhatsApp_Worker SHALL construct a text-type message with the transcript as the body and route it through the State_Router, preserving the existing session state, customer identity, and store context
3. THE Voice_Pipeline SHALL preserve all existing intent routing including stock lookup, price query, browse category, update price, view orders, and approval actions when the source is a voice transcript
4. WHEN the agent pipeline produces a text reply from a voice-originated message, THE Voice_Pipeline SHALL tag the reply with a `sourceChannel: 'voice'` indicator so downstream processing can generate a voice response

### Requirement 5: Reply Sanitization for TTS Input

**User Story:** As a WhatsApp user receiving voice replies, I want the spoken response to sound natural and clean without any system artifacts.

#### Acceptance Criteria

1. WHEN the Voice_Pipeline receives an agent reply tagged with `sourceChannel: 'voice'`, THE Sanitizer SHALL strip all JSON objects, XML tags, debug strings, stack traces, and internal error messages from the reply text
2. WHEN the Voice_Pipeline prepares text for TTS conversion, THE Voice_Pipeline SHALL remove WhatsApp-specific formatting markers (bold asterisks, emoji bullet prefixes, numbered-list formatting) that do not translate well to speech
3. WHEN the Voice_Pipeline prepares text for TTS conversion, THE Voice_Pipeline SHALL truncate the sanitized text to a maximum of 500 characters to keep voice replies concise for WhatsApp voice-note UX
4. IF the sanitized text is empty or shorter than 2 characters after processing, THEN THE Voice_Pipeline SHALL use a role-appropriate fallback message as the TTS input
5. THE Voice_Pipeline SHALL log the pre-TTS text length and whether any sanitization transformations were applied

### Requirement 6: Outbound TTS Generation via Gemini

**User Story:** As a WhatsApp user, I want to receive a natural-sounding voice reply so that I can listen to the response hands-free.

#### Acceptance Criteria

1. WHEN the Voice_Pipeline has sanitized reply text ready for speech, THE Gemini_Adapter SHALL convert the text to speech audio using Gemini TTS with a clear, conversational voice style
2. WHEN the Gemini_Adapter generates TTS audio, THE Gemini_Adapter SHALL produce output in a format convertible to OGG/Opus for WhatsApp voice note compatibility
3. WHEN the Voice_Pipeline receives generated TTS audio, THE Voice_Pipeline SHALL store the audio file in the Voice_Media_Bucket under the key pattern `voice/outbound/{userId}/{timestamp}.ogg`
4. WHEN the Voice_Pipeline stores outbound audio, THE Voice_Pipeline SHALL generate a pre-signed S3 URL with a 10-minute expiry for Twilio to fetch the audio
5. IF the Gemini TTS call fails or times out, THEN THE Voice_Pipeline SHALL fall back to sending the text reply as a standard WhatsApp text message
6. THE Gemini_Adapter SHALL support generating speech in the same language detected during transcription of the inbound voice note, where Gemini TTS supports that language

### Requirement 7: Outbound Voice Reply Delivery via Twilio

**User Story:** As a WhatsApp user, I want to receive the voice reply as a WhatsApp voice note so that I can listen to it naturally in the chat.

#### Acceptance Criteria

1. WHEN the Voice_Pipeline has a pre-signed audio URL ready, THE Twilio_Adapter SHALL send an outbound WhatsApp media message using the `mediaUrl` parameter pointing to the pre-signed S3 URL
2. WHEN the Twilio_Adapter sends a voice media message, THE WhatsApp_Sender SHALL persist the outbound message record with `messageType: 'audio'` and the associated session ID
3. IF the Twilio media message send fails after retry attempts, THEN THE Voice_Pipeline SHALL send the text reply as a standard WhatsApp text message instead
4. THE Voice_Pipeline SHALL preserve existing conversation and session tracking for voice-originated message exchanges
5. THE Voice_Pipeline SHALL log the outbound voice delivery with userId, Twilio message SID, audio file size, and delivery status

### Requirement 8: Graceful Fallback Behavior

**User Story:** As a WhatsApp user, I want to always receive a response even when voice processing encounters errors so that I am never left without an answer.

#### Acceptance Criteria

1. IF inbound audio cannot be downloaded or validated, THEN THE Voice_Pipeline SHALL send a short text clarification message asking the user to resend or type the request
2. IF transcription succeeds but TTS generation fails, THEN THE Voice_Pipeline SHALL send the agent's text reply as a standard WhatsApp text message
3. IF TTS generation succeeds but Twilio media delivery fails, THEN THE Voice_Pipeline SHALL send the agent's text reply as a standard WhatsApp text message
4. IF the Gemini transcription service is unavailable, THEN THE Voice_Pipeline SHALL send a text message informing the user that voice processing is temporarily unavailable and asking the user to type the request
5. THE Voice_Pipeline SHALL complete the full fallback chain within 30 seconds of receiving the inbound voice note to avoid user-perceived timeouts

### Requirement 9: Voice Media Storage and Cleanup

**User Story:** As a platform operator, I want temporary voice audio files cleaned up automatically so that storage costs remain controlled.

#### Acceptance Criteria

1. THE Voice_Media_Bucket SHALL store inbound voice audio under the prefix `voice/inbound/` and outbound TTS audio under the prefix `voice/outbound/`
2. THE Voice_Media_Bucket SHALL apply an S3 lifecycle rule that deletes objects under the `voice/` prefix after 24 hours
3. WHEN the Voice_Pipeline stores audio in S3, THE Voice_Pipeline SHALL tag each object with `mediaType: 'voice'` and `direction: 'inbound'` or `direction: 'outbound'` for observability
4. THE Voice_Pipeline SHALL log all S3 storage operations (put, presign) with the S3 key, file size, and content type

### Requirement 10: Role-Aware Voice Processing

**User Story:** As a platform supporting both sellers and customers on WhatsApp, I want voice messages routed to the correct agent pipeline based on the sender's role so that sellers get copilot responses and customers get shopping assistance.

#### Acceptance Criteria

1. WHEN the WhatsApp_Worker receives a voice message from a user with role `seller`, THE WhatsApp_Worker SHALL route the transcript to the Seller_Copilot for processing
2. WHEN the WhatsApp_Worker receives a voice message from a user with role `customer`, THE WhatsApp_Worker SHALL route the transcript through the State_Router using the existing session state
3. THE Voice_Pipeline SHALL use the `seller` audience for sanitization when the sender is a seller and the `customer` audience when the sender is a customer
4. THE Voice_Pipeline SHALL preserve existing demo identities and store routing for both seller and customer voice interactions

### Requirement 11: Observability and Tracing

**User Story:** As a platform operator, I want full tracing of the voice pipeline so that I can debug issues and monitor performance.

#### Acceptance Criteria

1. THE Voice_Pipeline SHALL emit structured log entries at each stage: audio received, audio validated, transcription started, transcription completed, agent reply generated, TTS started, TTS completed, outbound audio stored, outbound message sent
2. THE Voice_Pipeline SHALL propagate the request ID from the original webhook through all processing stages for end-to-end trace correlation
3. THE Voice_Pipeline SHALL publish CloudWatch custom metrics for: voice messages received count, transcription latency, TTS generation latency, end-to-end voice pipeline latency, fallback-to-text count
4. WHEN any stage of the Voice_Pipeline fails, THE Voice_Pipeline SHALL log the failure with the stage name, error message, userId, and request ID

### Requirement 12: Existing Text Message Behavior Preservation

**User Story:** As an existing WhatsApp user, I want my text message experience to remain unchanged so that the voice feature addition does not break current functionality.

#### Acceptance Criteria

1. WHEN the WhatsApp_Worker receives a text-type message, THE WhatsApp_Worker SHALL process the message through the existing seller or customer text handling flow without any changes to routing, session management, or response generation
2. THE Webhook_Handler SHALL continue to transform text messages, image messages, and document messages using the existing `transformTwilioToWhatsAppFormat` logic without modification
3. THE WhatsApp_Sender SHALL continue to send text-only replies for text-originated messages unless the user has previously interacted via voice in the same session
4. THE Sanitizer SHALL continue to apply the existing sanitization rules for all text-originated outbound messages without modification
